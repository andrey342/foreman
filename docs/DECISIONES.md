# Decisions

Decisions taken while implementing the plan (`docs/PLAN.md`), with date and reason. Where the build's `claude-code.d.ts` or the CLI disagrees with the plan, the build wins and the difference is recorded here.

## Phase 0 (2026-10-09)

**D-01 · Background sessions run in the shared checkout by default.** Claude Code isolates a `--bg` session in a git repo into a worktree (its first edit is refused until it calls `EnterWorktree`; see SPIKE §1). The plan assumes threads work in the repo's checkout (MSG has submodules, Docker and run files there; `maxParallelThreads: 1` serialises the work). foreman therefore launches with `--settings '{"worktree":{"bgIsolation":"none"}}'` and never writes `.claude/settings.json` of the repo. New profile key `isolation`: `"none"` (default) or `"worktree"` (Claude Code's own behaviour, for parallel threads).

**D-02 · `--bg` without `-p`.** The plan's launch line carries `-p`; the CLI refuses `--bg` with `--print`. The prompt goes as the positional argument.

**D-03 · Message to a thread = stop if live, then `--bg --resume` with no other flag.** `claude --bg --resume <sessionId> "<text>"` on a live session starts a copy under another id; on a stopped one it wakes the same id with its saved options and delivers the text; any other flag on the resume line starts a copy (SPIKE addendum), and the saved options already carry `--settings`. `send` stops a live session first, and refuses to touch a `working` one. No §10 stop: there is a way to deliver a message.

**D-04 · Usage comes from `assistant` rows, deduplicated by `message.id`.** Background transcripts have no `result` row. Each API message is split into one row per content block, each with the same `usage`. A turn ends at a `system` row with `subtype: "turn_duration"`.

**D-05 · Type-checking.** `tsc` is not installed on the machine and `.claude-plugin/types/` is laid only by an interactive load. The repo carries `typescript` as a dev dependency (`npx tsc -p .`) and a script that copies the build's `claude-code.d.ts` into `.claude-plugin/types/claude-code/` when the engine has not laid it (git-ignored, regenerated, never edited).

**D-06 · `claude` from PATH.** `$.process.run(['claude', …])` resolves `claude.exe` from PATH on Windows; `claudeExe: null` means `'claude'`.

**D-07 · The plugin lives in this repo, not in the session's mods folder.** The plugin-authoring skill writes mods under `~/.claude/dev-mods/<session>/`; the user asked for `C:\Users\javi-\source\repos\foreman`, loaded with `claude --plugin-dir`.

**D-08 · Spike cwd.** The spike ran in a scratch folder of this repo, not in `C:\MSG` (nothing may be written there before Phase 5) nor in `foreman-demo` (not trusted yet: `--bg` refuses an untrusted workspace).

**D-09 · Haiku alias.** The plan's D4 names "Haiku 4.5" for panel summaries; the `haiku` alias resolves to `claude-haiku-5-5` on this build. Profiles use aliases (`haiku`, `sonnet`, `opus`, `fable`), not ids.

**D-10 · `claude logs` is a screen, not a log.** It prints the session's terminal with ANSI escapes. `/foreman log` strips them and keeps the last n non-empty lines.

## Phase 1 (2026-10-09)

**D-11 · Every call on `$` lives in `hooks/register.tsx`.** `claude plugin validate` refuses `$` passed to a function imported from another file ("$ is followed only into a function declared in this same file, never across an import"), and `update`/`read` need atoms declared in the same file. So `hooks/lib/*` and `hooks/ui/*` are pure (data in, data or element trees out: the pane gets the surface's element table, not `$`), and `register.tsx` holds the atoms, the `$` helpers and the hooks. The plan's file list stays; only where `$` is touched moves.

**D-12 · The spike's test is not a test of this plugin.** `claude plugin test .` runs every `*.test.ts(x)` under the folder, `spike/mod` included, where the spike plugin is not loaded. It is kept as `spike/mod/hooks/pane.spike.tsx` (it passed in Phase 0, commit a8832b9; rename it to `.test.tsx` and run `claude plugin test spike/mod` to repeat).

**D-13 · No `userConfig` yet.** Nothing global is needed so far: everything per repo is in the profile, and `claudeExe` defaults to `claude` from PATH. A `userConfig` field is added when a global setting appears.

**D-14 · The pane lists background sessions only.** Interactive chats appear in `claude agents --json` too; the pane shows `kind: background` rows under the repo root (worktrees included), live ones and exited ones from the last 7 days, grouped Working / Waiting for you / Done / Stopped. The status line counts live ones only.

**D-15 · Tested build.** The engine laid the 2.1.296 declarations at the first interactive load; `tsc -p .` runs against them. `scripts/sync-types.mjs` fills the folder from the skill bundle when no interactive load happened yet.

## Phase 2 (2026-10-09)

**D-16 · Command names follow §4 (English).** The Phase 2 list of the plan says `lanza, di, abre, log, para, cierra, estado`; the commands are `launch, tell, open, log, stop, close, status`, as §4 and the user's rules ask.

**D-17 · Thread state from a finished turn (corrected after review C-01).** `claude agents` says `done`; the transcript decides. foreman stamps `sentAt` on the thread when it launches it and at every `/foreman tell`, and reads the `foreman-result` only when the transcript holds a prompt written at or after `sentAt` with a `turn_duration` after it; `lastText` comes from the assistant rows after the last prompt only. Until then the thread stays `working`: after a resume the job's `state` never passes through `working` and the new prompt lands about 2 s later (SPIKE addendum), so neither the row nor an old turn end may close the new turn. A message that has not reached the transcript three minutes after `sentAt` leaves the thread `waiting` ("the message never reached the thread"). Then: a valid block with `done` → `ready` (needs review), or `done` for the self-closing roles `free` and `triage`; `question`/`blocked` → `waiting` with the question; `failed` → `failed`; no block or a broken one → `waiting` with `noResult` and the reason, never an invented done.

**D-18 · Usage is counted incrementally (corrected after review C-06).** Each sync adds the usage of assistant messages newer than the thread's `usageSince`, once per `message.id`, and skips the rows of `usageLastId`, the last message already counted: one message is written over several rows a second or more apart, so a read can fall between them. A transcript read through its tail (over 3.5 MB) still adds up.

**D-19 · Registry.** Threads live in `$.store` under `threads:<repo root, normalised>` (the registry every chat shares, D-25) and in `$.state` (`foreman.threads`, this session's copy). A thread launched with `--run <id>` is also written, with every transition, to `<runsDir>/<id>/foreman.json`. `onRunCreate` runs in Phase 5.

**D-20 · `maxParallelThreads` counts busy foreman sessions, whichever chat launched them (corrected after review C-02).** Busy: a live row of `claude agents` under the repo named `foreman:*` that is `working`/`blocked` (or `busy`/`waiting`), plus a registry thread just launched that the CLI does not list yet. A thread waiting for an answer, ready for review, failed or exited does not hold a slot.

**D-21 · No prefix in status and toasts.** The engine already draws them under the plugin's name (`⚠ foreman: foreman: 1 working` was seen), so the texts carry none.

**D-22 · PowerShell 5.1 and inner quotes.** Passing `'/foreman launch free "…"'` from PowerShell 5.1 to `claude.exe` mangles the inner double quotes; foreman's argument parser takes single quotes too (`'/foreman launch free ''…'''`). Inside a Claude Code session the prompt box has no such problem. For the README's troubleshooting.

## Phase 2 review (2026-10-10)

**D-23 · Review findings deferred.** C-13 (`claudeExe` from the repo's profile runs at `session.start` and every 30 s): kept for now, the same trust a project's settings hooks get once the workspace is trusted; Phase 6 moves `claudeExe` to `userConfig` and stops reading it from the repo. C-15 (`LIMIT_RE` matches the model's own words): goes with Phase 4, where `limit` starts an automatic retry; until then it only labels a thread whose turn ended without a block. C-17 (reviewer and critic have `Bash` and `Write`): goes with Phase 3's guards.

**D-24 · Rules every thread gets (review C-05).** `prompts/_rules.md` (no push, pull request, merge, tag or release unless the assignment says so in writing; stay in the repo and the task) is appended to every role's brief before the result contract, and `/foreman tell` adds the same rule to every message.

**D-25 · `$.store` is the shared registry (review C-02).** Every chat of the repo runs its own watcher. Each write re-reads the store and merges by id (the later `updatedAt` wins, then the later `usageSince`), and every sync and command first pulls the store into the session's copy, so a chat never drops a thread another chat launched and sees its changes. A transition the run file already ends with for that thread is not appended again. The read-merge-write is not atomic across processes: two chats writing in the same instant can still lose one write, which the next sync repairs from the CLI and the transcript.

**D-26 · The Windows tail script is fixed (review C-08).** `powershell.exe -NoProfile -NonInteractive -Command <script>` reads the path from `$env:FOREMAN_TAIL_PATH`, passed through `ProcessRunInit.env`; no path is spliced into the script. It is the one place foreman runs a shell, because Windows has no `tail`; elsewhere `tail -c`. Checked on a real 4.5 MB transcript (SPIKE addendum).

**D-27 · The registry stays small and run files are never lost (review C-14).** Results are cut to 2,000 characters per text and 50 entries per list, `waitingFor` to 300; closed threads are dropped after 14 days. A run `foreman.json` that does not parse is copied to `foreman.json.broken-<time>` before a new one is written, with a line in the transcript.

**D-28 · One sync at a time, shared (review C-09).** The module keeps the promise of the sync in flight: the watcher, Refresh and launch join it, and `/foreman status` and opening the pane wait for it and then run a fresh one, so they never print what is about to be replaced. It is a module value: a reload loses it, which at worst lets two syncs overlap, and D-25's merge absorbs that.

**D-29 · Work root and repo root (review C-16).** The session's own checkout (`$.session.root()` when it holds a `.git`, as a worktree does; else the repo root) is where threads run and where `.claude/foreman.json` and `runsDir` are read. The main working tree (`$.session.repo().root`) keys the registry and filters the pane, so the threads of every worktree of a repo show together.

**D-30 · Skills that do not exist (review C-11).** At launch foreman lists the session's commands (skills are among them, a plugin's as `plugin:name`) and leaves out of the brief every profile skill it does not find, saying which in the command's answer. When the list cannot be read, all are kept.

**D-31 · `failed` sessions (review C-03).** `claude agents` can say `state: "failed"` (a launch cut short while starting). The thread becomes `failed` with the reason and frees its slot; the pane has a Failed group; a session that exited while `blocked` (no `pid`) is shown as stopped, not as waiting for the user. The projects folder is scanned for a transcript only while the session is live.

**D-32 · Commands never fail silently (review C-12).** A `/foreman` command's errors come back as its answer (`/foreman <args> failed: <reason>`). A `tell` whose stop went through but whose resume did not marks the thread `stopped` ("a message failed to resume it"). A brief or message over 30,000 characters is refused before Windows' 32,767-character command line would refuse it.

## Phase 3 (2026-10-10)

**D-33 · Agent prompts live in `prompts/agents/`, not in the plugin's `agents/` folder.** A plugin's `agents/*.md` files are declared to the model as agent types it may spawn by itself, with their frontmatter's model and effort and outside foreman's record. foreman instead registers `foreman:reviewer` and `foreman:critic` with `$.agent.register` at `session.start` and again before each review, from `prompts/agents/<role>.md` (the system prompt) and the profile (model, effort, tools, skills, permission mode: the profile wins). An `agent.offer` hook hides both types from the model, so only foreman spawns them. `triage` and `qa` are not registered: `qa` is a thread role (D4) and nothing spawns `triage` yet (plan §12).

**D-34 · The reviewer guard (review C-17).** A `tool.call` hook judges the calls whose `agentId` is a review foreman started (its record), or, when the record has not landed yet or the model spawned the type, an agent `$.agent.list()` shows as `foreman:reviewer`/`foreman:critic` (such an agent may read but not write). Edit, MultiEdit and NotebookEdit are refused; a tool outside the role's `tools` is refused; Write passes only when the file's real path (the d.ts `placed` rule: the file's, else its folder's plus the name) is under the real path of `<runsDir>/<runId>/`; Bash and PowerShell pass only when every segment (split at `&&`, `||`, `|`, `;`, newlines, outside quotes) starts with a read-only program (git with a read-only subcommand and no `-c`, `--output`, `--ext-diff`; rg without `--pre`; grep, ls, cat, head, wc, find without `-exec`/`-delete`, Get-Content, Get-ChildItem, Select-String and the like) and the line has no redirection (stderr to null or to stdout excepted), substitution, script block, background operator or environment assignment. Its `.catch` refuses a subagent's call it could not judge and lets the main loop's through. Reviewers therefore cannot run tests (`node test.js`, `dotnet test`): they say which gates the implementer must run (plan §7: "sin ejecutar gates que muten"). A profile list of extra allowed commands is left for later.

**D-35 · Subagents run in their role's permission mode.** The subagent inherits its parent's mode unless its type sets one. Live in a `claude -p` parent (nobody to answer a dialog) every Bash and Write of the reviewer was denied by permissions and it ended with no file (recorded `noResult`). foreman registers the types with the role's `permissionMode` (`auto` by default, as threads): the guard bounds what they may do, the mode spares the person a dialog per read-only command. A profile that wants dialogs sets `roles.reviewer.permissionMode: "manual"`.

**D-36 · The subagent's id.** `$.agent.spawn` resolves `{ model, agentId }` as the subagent starts; its answer is its `turn.complete` with that `agentId` (plan §11). Pending reviews are kept by `agentId` in `$.store` (`reviews:<repo>`) and `$.state`, so a reload keeps the wait; at `session.start` a review whose subagent is no longer in `$.agent.list()` is settled `noResult` ("the subagent ended before it answered"). When `spawn` answers without an id (the test kit keeps the id to core), foreman takes the newest agent of that type and description from `$.agent.list()`.

**D-37 · Review files, numbers and verdicts.** `<runsDir>/<runId>/review-<part>-r<n>.md` and `critic-<part>-r<n>.md`; `n` is one past the highest taken by a file or by a record (a review that wrote no file keeps its number). The file decides: its first non-empty line must read `Verdict: OK|NO|BLOCKED` (`PASS|FAIL|BLOCKED` for the critic; `Veredicto:` is accepted for repos that write Spanish); a missing file or a first line without a verdict is `verdict: none`, `noResult`, never OK. The final JSON of the answer is read too; when it disagrees with the file, the file stands and the difference is noted. Findings are the distinct `C-nn` ids that open a heading, a list item or a table row. Each review is recorded, started and settled, in the run's `foreman.json` under `reviews`, in the transcript (one line) and as a toast. `--run` and `--part` default to the latest thread's; `--base` to `origin/HEAD`, else `HEAD~1`.

**D-38 · `/foreman review --thread` is not in Phase 3.** A reviewer run as a background session would be outside this session's `tool.call` guard (it is another process), so the guard of D-34 could not hold "writes only under runsDir". It comes back, if needed, with a settings-level guard passed by `--settings` (permission rules), not before. `--deep` stays in Phase 6.

**D-39 · N-01 kept.** A `working` row without a `pid` (a session still starting) is shown under Stopped / exited for a few seconds; cosmetic, left as it is.

## Phase 3 review (2026-10-10)

**D-40 · The reviewer guard, corrected (review C3-01, C3-02, C3-05; supersedes the shell part of D-34).** PowerShell is no longer among the default `tools` of reviewer and critic: a parenthesised argument is an expression in PowerShell (`Get-Content ([IO.File]::WriteAllText(…))` wrote a file in the review's probe), and Git Bash already gives `git` and `rg`, with Grep, Glob and Read for searching. For a profile that adds it back, the PowerShell line is also refused on `( ) [ ] @ $` outside single quotes. For both shells the line is read quote by quote: single quotes are literal; inside double quotes `$` and the backtick are refused; outside quotes redirection (stderr to null or to stdout excepted), `$`, the backtick, parentheses, braces and a lone `&` are refused, so searches such as `rg "=>"`, `rg 'f() {'` or `rg 'List<T>'` pass. Every segment must start with a bare program name (no `/` or `\`, no `.exe` stripped) from a short list checked option by option: git (read-only subcommands, no `-c`, `--output`, `--ext-diff`), rg (no `--pre`, `--hostname-bin`, `--search-zip`/`-z`), grep, ls, cat, head, tail (no follow), wc, pwd, echo, find (no `-exec`, `-delete`, `-fprint`…), stat, diff, and a few read-only PowerShell cmdlets; uniq, tree, file, less, more, sort and the rest are gone.

**D-41 · One owner per shared record (review C3-03; the mechanism N-02 needs in Phase 4).** `hooks/lib/owner.ts`: a record carries the session that started it (`$.session.id()`); `standing(owner, me, rows)` says `mine`, `other` (another session `claude agents` lists alive) or `orphan` (no owner, or its session gone; a `claude -p` run is never listed, so its records turn orphan at once). At `session.start` a review still waiting is settled only when it is this session's and its agent is gone, or an orphan; another live session's is left alone. It is settled from its file (`settledBy: 'file'`): a verdict there stands. A settlement from the file gives way to the subagent's own answer if that still comes (`settledBy: 'answer'` ranks above `'file'`, which ranks above pending, in every merge of the store).

**D-42 · The guard's `.catch` (review C3-04).** When the guard fails, a call of an agent already known to be someone else's (listed and not of a foreman type) goes on; a call of a foreman reviewer or critic, or of an agent nobody could place, is refused. In the normal path an agent the list does not show is not guarded: a workflow's agents are not listed, and treating them as reviewers would refuse their edits.

## Phase 4 (2026-10-10)

**D-43 · The cycle is a pure state machine (`hooks/lib/cycle.ts`).** Its header holds the transition table of plan §5, and `cycle.test.ts` walks it row by row. Phases: `implementing`, `reviewing`, `applying`, `ready`, `waiting`, `limit` (added: the implementer is at a usage limit), `closed`. `waiting` says on what: the thread (a dialog, a question, a blocker, no result, a failure: re-read at every look, so it goes on when the thread does) or the person (NO with the rounds used up, BLOCKED, no verdict: only a message the person sends the implementer after the wait sets it going again). A thread result counts for a phase only when it is newer than the phase (`phaseAt`), so a ready from an earlier round is never read as the new round's. Rounds count the reviews bound to the cycle: NO with `rounds < maxCycles` applies, NO on the last round waits ("review rounds used up (n of max): decide"). blocked and question only ever lead to waiting; foreman never answers them. The resume sends the review file's path and fixed instructions only. Every phase change is written to the run's `foreman.json` (`transitions`, `thread: "cycle:<part>"`, with its time) and the cycle itself to its `cycles`.

**D-44 · One owner per cycle, effects that can repeat (review N-02).** A cycle belongs to the session that started it (`owner.ts`); another live session leaves it alone. An orphan (owner gone, or a `claude -p` run, never listed) is claimed by the first session that sees it, and driven from that session's next look, so two sessions that claim it at once settle on the store's last write before either acts. What a phase needs done is derived from the record, not only from the transition, so an adoption or a reload finishes a half-done effect and never repeats a done one: `reviewing` records `reviewRequestedAt` before the reviewer is spawned, and a review of the run and part started at or after it is bound instead of starting another; `applying` records `applyFor`, and a thread whose `sentAt` is at or after the phase already got its resume. One cycle per run at a time; one implementer alive through `maxParallelThreads` (D-20).

**D-45 · Usage limits from the API error row (review C-15).** The thread is `limit` when the last assistant row of the turn foreman waits for has `isApiErrorMessage: true` and `error: "rate_limit"` (SPIKE addendum); its `retryAt` is `quotaLimits.resetsAt` plus a minute (30 minutes from now when the row carries none). Any other API error row (401 …) makes the thread `failed` with its status. `retryAt` lives in the registry, in `$.store`: every watcher look, in any session, retries a thread whose reset has passed (its owner; an orphan is claimed first), and `session.start` also sets a `$.clock.after` for the earliest reset, so a reload loses nothing. The retry tells the thread "The usage limit has reset. Go on where you stopped…". The text heuristic `LIMIT_RE` is gone.

**D-46 · `notify.command` (plan §6).** Split into argv with the same quoting rules as foreman's commands (no shell), `{{message}}` in it replaced by the notice, else the notice appended as the last argument; 15 s at most; a failure goes to the debug log. Like `claudeExe` (C-13, D-23) it is a command named by the repo's profile and runs without the person typing; Phase 6 moves both to `userConfig` or confines them.

**D-47 · A reviewer's hand-back does not wake the chat's model.** Seen live: each reviewer that ended handed its report back to the session as a peer prompt, and the chat's own model (Opus, high) took a turn to "check the claim". foreman settles the verdict from the file at `turn.complete`, so a `prompt.submit` hook drops the hand-back of a review it knows (by `senderTaskId`/`from`), with the reason shown to the person: plan D3 wants no model in the coordinator. Any other peer message passes; the hook's `.catch` delivers.

**D-48 · Night mode (`/foreman night on|off|status`, per repo).** On: cycles started then, and active ones, get one more review round; a part that ends `ready` starts the cycle of the plan's next part (lines like `## Part B`, `Parte B:`) unless a pause is written on that part's heading or in the three lines before it (pause, stop, halt, parada, pausa, para aquí); thread toasts and cycle toasts are kept in a night log instead of shown (`notify.command` still runs). Off: the log is printed and cleared. Closed stops (a question, a blocker, rounds used up, BLOCKED) still stop.

**D-49 · What a cycle runs on.** `/foreman cycle <plan> --part A [--level N2] [--cycles <maxReviewCycles>] [--run <id>] [--model m]`; the run id defaults to `<yyyymmdd>-<plan file name>`. The base is `git rev-parse HEAD` when the cycle starts; every review reads `<base>..HEAD` plus `git status` (uncommitted work is a finding) and, from the second round, checks the previous review's findings (`{{previous}}`). The implementer's brief now asks it to commit with explicit paths before ending each turn. The reviewer of a round runs in the cycle owner's session: when that chat closes mid-review, the review is settled from its file (C3-03), possibly without a verdict, and the cycle waits.

**D-50 · The live acceptance's fixture.** foreman-demo got an untracked `.claude/foreman.json` for Phase 4: implementer N1 and reviewer on Sonnet (cost), and a reviewer-only house rule ("every exported function carries a JSDoc block … a missing one blocks") that the implementer does not know, so the first review says NO for a reason a real repo has (a convention only the reviewer checks) and the cycle walks NO → apply → OK. It is removed before Phase 6, which checks foreman-demo without a profile.

**D-47, note (review P4-01).** The hand-back is recognised by `origin.kind === 'peer'`, `origin.handback === true` and `origin.senderTaskId`/`origin.from`: fields observed at run time in 2.1.296 (SPIKE addendum, Phase 4) that its d.ts does not declare on the peer origin. Check them again with each build; if they change, the hook stops recognising hand-backs and they are delivered (it fails open). A composer prompt of the same shape is never held back (test).

## Phase 5 (2026-10-10)

**D-51 · foreman inside its own threads (review of Phase 4).** Installed at user scope, or passed with `--plugin-dir`, foreman loads in every thread it launches too. Each thread is launched with `env.FOREMAN_THREAD = <thread name>` in its `--settings` (kept on resume with the saved options); foreman reads it (`$.env.get('FOREMAN_THREAD')`) and runs in thread mode: the profile's guards act on every call, the session section names the thread and its run's notes, and nothing else runs (no /foreman, no watcher, no adoption of cycles or limits, no write to `$.store` or to a run file). The status line says so. When foreman runs from a folder (`--plugin-dir`) rather than an installation under the configuration's `plugins`, a thread is launched with the same `--plugin-dir`, so the guards act there too.

**D-52 · The profile's guards (plan §8).** `guards.ts` implements the two kinds: `requireToolCalledBefore` (the tool, a name or pattern, must have been called in the session before the matching call; the session's called tools are kept in `$.state`) and plain rules (`pathGlob` / `commandRegex`, every named condition must hold); `mode: "warn"` lets the call run and tells the model (a note appended to its conversation, as the old settings hook's `additionalContext`) and the person (a toast), `mode: "deny"` refuses it. `pathGlob` is read against the path relative to the work root, `/` separators, case-insensitive; `**` spans folders. A path guard written for the file tools (Edit, Write, MultiEdit, NotebookEdit) also holds for a Bash or PowerShell command that writes a matching path: seen live, a thread edited `test.js` with `sed -i` past a guard on Edit. That match is by spelling (redirection targets, the arguments of `tee`, `cp`, `mv`, `rm`, `Set-Content`, `Out-File`… and the files of `sed -i`/`perl -i`), best effort; the file tools are matched exactly. The engine takes one `tool.call` hook without a matcher per module, so the reviewer guard (D-40) and these share it; its `.catch` refuses a call it could not judge when it belongs to a foreman reviewer or an unplaced subagent (C3-04), or when the profile declares guards, and lets it run otherwise. The MSG profile covers both rules of `gitnexus-guard.js` (impact before a `.cs` edit, detect_changes before `git commit`, both warn) and adds `git add -A` → deny.

**D-53 · `hooks.onRunCreate`.** Run once, when foreman first creates a run's folder (a launch or a cycle with a `--run` it has not seen): by argv with foreman's quoting rules (no shell), `{{runId}}` replaced, in the work root, two minutes at most; its argv, exit and output go to the run's `foreman.json` under `hooks`. A script the command names (`*.ps1`, `*.sh`, …) that does not exist is skipped with a note (D8); a non-zero exit stops the launch before any thread starts, with the output. `profiles/msg.json` carries MSG's `new-run.ps1 … -JoinBranch`; it is to be tried with `-DryRun` first (docs/PENDING.md).

**D-54 · The session section (plan §3, `prompt.compose`).** A `session`-scoped section `foreman:session`: in the main chat, the active cycles and the threads waiting for the person, and nothing when there are none; in a thread, its name, role and part and, with `injectHandoff` on (the default; MSG's profile turns it off, its own hook injects the handoff), where its run's `handoff.md` and `report.md` are. It carries no time, so it changes only when that state does and the prompt cache holds.

## v0.2 Phase 0 (2026-10-16)

Spikes for `docs/plans/plan-foreman-v0.2.md` §9 Phase 0; evidence in `docs/SPIKE-v0.2.md`. The desktop app runs its own Claude Code build (2.1.295) while the CLI is 2.1.296; both were exercised.

**D-83 · A subagent cannot be moved into the plan's worktree (plan D-73, A-01).** `$.agent.spawn({ cwd })` does not change where the subagent runs: with `cwd` set to a worktree it answers `pwd` = the repo root, branch `main`, and a relative Read fails with "your current working directory is <root>" (2.1.296, `-p`). `EnterWorktree({ path })` from the subagent is refused ("switching is only available to sessions whose working directory is inside a worktree"), and an `isolation: 'worktree'` subagent is pinned in a new worktree of its own (left on disk with its branch afterwards) and refused write access to the plan's. **D-84 · Reviewer and supervisor run as `claude -p` processes, not subagents (plan D-68, D-73) — pending the reviewer's OK.** In a desktop session in `auto` permission mode (the user's default), every plugin call that goes through the auto-mode classifier is refused with "gave no verdict … the request that produced this action did not ask for one": `$.agent.spawn` from an autonomous flow and from a pane button press, `$.session.send`, and `start_session` through `$.tool.call` and `$.mcp.call`, even inside a command the person typed. `$.process.run` is not a tool call and is not classified. A `claude -p` process started by `$.process.run` with `cwd` = the plan's worktree works from the CLI and from the app (relative Read, `pwd` and branch are the worktree's), and its guard is its flags: `--permission-mode dontAsk` plus `--allowedTools` with the read-only tools and the exact gate lines refuses everything else without a dialog (Write was denied, `npm test` ran; Claude Code still lets read-only git commands through). The prompt goes in by stdin (`--allowedTools` takes several values and swallows a positional prompt); `--output-format json` gives the result, `usage` and cost; foreman writes the review file from the result, so the reviewer needs no write tool. `--bare` is not usable (API key only). Further probes: the process must force `--permission-mode dontAsk` — under `auto` the classifier let a Write through although `--allowedTools` did not list it (under `default` it was denied without a dialog); `--settings '{"env":{"FOREMAN_THREAD":"foreman:<plan>:reviewer-<part>"}}'` reaches `$.env.get` in the process, so the plugin's own guard runs inside it (a Write was denied by the plugin); the undocumented `--max-turns` works (`"subtype":"error_max_turns"`, empty `result`: for the supervisor that is an escalation); `$.process.spawn` runs the reviewer with no 10-minute cap and its JSON is read from stdout, while the supervisor, short, uses `$.process.run`; if the coordinating chat closes mid-review the child dies with the module and foreman re-runs the review on reopening (idempotent). Cost: on a small diff with Haiku the process took 16–23 s and 0.004–0.006 USD against 12.7 s for the subagent, carrying about five times the context (Claude Code's whole system prompt and tool set, mostly cache reads); Phase 4 trims it with `--tools` and, if needed, `--system-prompt-file`. A gate line that is not literal (`npm test; echo "EXIT=$?"`) is denied under `dontAsk`, which the brief and D-73's "could not run" rule must cover. This replaces `$.agent.register`/`$.agent.spawn` for the reviewer and the supervisor (and with them the `turn.complete` matching and the hand-back hooks) and makes D-83's variant unnecessary.

**D-85 · Thread driver: `background`; "Open" puts a thread in the app (plan D-69) — the first half decided by the plan's own order, the second pending the reviewer's OK because of the user's answer 3 in Annex C.** The plugin cannot create a desktop session: (a) `$.tool.call(start_session)` and (b) `$.mcp.call("ccd_session","start_session")` are refused by the classifier; `claude --desktop` refuses redirected output and only opens an existing session; (c) the chat's model may create one only in a turn the person opened with their own words ("Start sessions only on the user's own words to you here; this turn runs an automated event, another session's message, …"), so it would cover only the first launch of a plan, never the next part or the apply round. `claude --bg` works in the plan's worktree with `bgIsolation: none` (commit on the plan's branch, the repo's skill and hook in use, no new trust prompt). ## v0.2 Phase 1 (2026-10-16)

The generic core: `/foreman go` over a plan's parts, the version 2 profile, storage under `.git/foreman/`, an efficient watcher. Decisions the plan left open, in the order they came up.

**D-89 · Where foreman keeps a run (D-70, made concrete).** A plan run's folder is `<git common dir>/foreman/<slug>/` (or the repo's own `runsDir`, or `~/.claude/foreman/<slug>/` outside git; `lib/storage.ts`, separators normalised to the work root's). Review files are recorded by absolute path. A runsDir folder is still checked to resolve inside the work root (C-04); `.git/foreman/` needs no such check, no repo can link it away.

**D-90 · Until Phase 4 every plan runs in the checkout.** The profile already takes `isolation: worktree | branch | none` (D-71), but the default is `none` until Phase 4 brings foreman's own worktree and branch and flips it to `worktree`; a profile that names another value gets one line from `go` saying the plan runs in this checkout for now.

**D-91 · The surface in this phase (D-75, in steps).** Gone now: `cycle` (→ `go`), `night`, `critic`, `review --deep`, `hooks.onRunCreate`, the roles `planner`, `critic`, `qa`, `triage`, `free`, and levels; each 0.1 command answers with what replaces it, and `--level` says to pass `--model`. **D-92 · Reading a plan (D-76, the details).** A part's id is the word after Part/Parte/Phase/Fase/Step/Paso/Stage/Etapa/Milestone/Hito with trailing dots and dashes dropped (`2b`, `A`); with no part headings, the `##` sections after the heading that names the steps are parts `1`, `2`…, and with none of those the whole file is part `1`. A part's text runs to the next heading of its level or higher. Its criteria are the list under a heading or a bold line naming acceptance, criteria, done-when or verification, and also under a plain label line that starts with one of those words and ends in a colon (`Aceptación:`, as this very plan writes them). A pause applies before part N+1 when a pause heading or a line starting with the pause word lies between the headings of parts N and N+1, or when part N+1's own heading names it; `/foreman resume` is the person's answer to it and starts that part at the next look.

**D-93 · `go` asks once, inside its command (D-76).** `go` shows the parts it found (id, title, how many criteria, the pauses) in a `$.ui.ask` dialog, "Run them" or "Cancel", from its own `command.run` (F0-7: works in the app). `--parts` names the parts and skips the question, and so does `--yes`. Where no dialog can be shown (a `-p` run) `go` starts as asked and its answer says it was not confirmed. A run's id is the plan file's slug, with `-2`, `-3`… when the slug is taken by a folder or a run (A-16).

**D-94 · How a plan moves on (run.ts).** Each part is a cycle of its own, on its own implementer thread, from the commit HEAD is at when it starts, so its review reads only its commits. The run is driven by the owner of the session that started it, with the same claim-then-act rule as cycles (an orphan is claimed on one look and driven from the next): a part ready starts the next one unless the plan pauses before it or the person paused the run; the last part ready ends the run (`done`, said once); a next part that cannot start pauses the run with the reason. `pause` stops the chaining only: the part in progress goes on. One plan is active per repo: `go` of the same plan answers with its state, of another plan is refused (D-71).

**D-95 · Counting findings (A-10).** The count is the largest of: distinct `C-nn` ids that open a heading or a list item; `##`–`######` headings after the verdict line that are not a "what I checked", notes, summary, gates or scope section (English or Spanish); and `Finding N` / `Hallazgo N` lines. When that gives 0 on a NO, the reviewer's final JSON count stands. The `C-nn · P1` format stays as the reviewer prompt's suggestion only.

**D-96 · Guards in version 2 (D-78).** `guards` is `{ "scope": "threads" | "everywhere", "rules": [...] }`; a 0.1 list is read as the rules with scope `threads` and one warning saying so (the 0.1 behaviour, every session, is `everywhere`). The rules act only where their scope says; the hook's fail-closed paths (a rule that could not be judged; a profile that declared guards and cannot be read, P5-02) act only there too, so a broken profile no longer blocks the main chat when its guards are for threads. The reviewer guard is foreman's and the profile cannot change it: the reviewer's tools are fixed (`roles.*.tools` retired with a warning).

**D-97 · The watcher's pace (D-79, M6).** Every 30 s each chat reads the store (threads, parts, plans), so its pane shows what another chat started. It lists `claude agents` and reads transcripts only while something of the repo is open (a thread not done, stopped or failed; an active part or plan; a pending review), when a command or the pane asks, or every 5 minutes otherwise. A transcript whose size and mtime did not change is not read again: its facts are reused with no new usage. The profile is read again only when its mtime or size changed (one `stat` per tool call instead of an exists and a read), and the session's roots, its git folder and its thread marker are read once per load (A-04). Toasts for a thread's move and a settled review come only from their owner (A-11); a part's notices only ever came from its owner.

**D-98 · `profiles/msg.json` goes now, not in Phase 5 (D-81, earlier).** It was a 0.1 profile built on keys 0.2 retired (levels, `repos`, `onRunCreate`, `injectHandoff`), and `scripts/check-profiles.mjs` fails on any warning: with it the script could not pass with `default.json` version 2 (criterion 6).
